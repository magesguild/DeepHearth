# From Alpha 4 to the Basin Core

*Research note: Deep Hearth as the reference implementation for a generic,
physical game engine.*

## Thesis

Deep Hearth is not only a game. It is the reference body from which a generic
Basin engine can be distilled.

We are not designing the bare-metal engine from abstraction alone. We are
observing what survives when many kinds of worlds pass through the same body:

```text
Forgotten Realms
-> campaign modules
-> towns and dungeons
-> monsters and communities
-> Magic and cardless hosts
-> familiars and organs
-> future digital worlds
-> irreducible physical game engine
```

The engine is discovered by conversion. Every host world asks what it must
preserve in order to remain itself while entering Deep Hearth.

## Deep Hearth's Role

Deep Hearth is Basin's CP/M 2-style reference implementation: bounded, hand-
runnable, inspectable, replayable, repairable, and joyful.

Its job is not to contain every future setting. Its job is to make the kernel
visible in a living body so that later distillation is earned by use rather than
guessed from theory.

Alpha 4's Responsive Neighborhood is especially important because it tests the
kernel across:

```text
person
-> job
-> relationship
-> household
-> community
-> economy
-> ecology
-> terrain
-> memory
-> return
```

If those scales can share one physics without becoming bookkeeping layers, the
kernel is becoming legible.

## The Conversion Layer

An existing campaign or game world can receive a Deep Hearth projection:

```text
host world
-> entities, places, jobs, resources, maps, rules
-> cells and local laws
-> membranes and capabilities
-> relationships and community roles
-> T-Stops, witnesses, and State Capsules
```

The host world remains the content layer. Deep Hearth supplies the state,
agency, provenance, ecology, memory, and return layer.

Examples:

```text
existing NPC
-> job stamp
-> need and boundary
-> knowledge scope
-> relationship hooks
-> persistent body when touched

existing monster
-> habitat
-> needs and senses
-> resources and legal responses
-> ecological role
-> Rest and recovery

existing deity
-> domain
-> worship relationship
-> rites and offerings
-> permissions and obligations
-> miracles and refusal

existing campaign module
-> player entry
-> GM hidden state
-> scenarios and escalation
-> treasure and growth
-> State Capsule return points
```

The conversion layer allows players and GMs to bring worlds they already love
into the Basin without rebuilding their content from scratch.

## Irreducible Engine Surfaces

Across conversions, the recurring irreducible structures are:

```text
cells
perception and projection
membranes
jobs and capabilities
resources and flows
boundaries and refusal
local physics
Gravity and attractors
Dark Matter and hidden state
Antimatter and incompatibility
Phase and synchronization
events and entropy
relationships
T-Stops
witness
Rest
State Capsules
host adapters
```

The generic engine does not need to retain the host's names. It needs to retain
the host's lawful transitions and the source of every durable result.

## Universal Action Loop

The smallest cross-host loop is:

```text
notice
-> declare intent
-> identify a legal transition
-> pay or commit
-> resolve uncertainty if needed
-> change state
-> leave a trace
-> continue, stop, or Rest
-> return later
```

The same loop can operate a spell, a negotiation, a route, a market exchange, a
monster encounter, a familiar request, a job task, a community repair, or a
portal crossing.

## Physical Registers

The distilled engine should run with ordinary materials:

```text
figure -> body or cell
card   -> capability, hidden state, job, relationship, or host packet
cord   -> relation, route, lineage, or witness
ledger -> memory and State Capsule
```

No material has a universal meaning outside its declared scene contract. The
table assigns a role, uses it to compute a meaningful future, and witnesses the
result.

## What Does Not Belong in the Kernel

The generic engine does not need to contain:

```text
Waterdeep
Alchemist
Baker
Magic
the d20
a particular map
a particular language
a particular god
a particular monster
```

Those are host content, setting projections, or adapters. They may be rich and
specific while the engine remains small.

The kernel should not preserve:

```text
universal NPC simulation
complete market calculation
complete linguistic database
full tectonic modeling
continuous updates for dormant systems
```

It preserves the contract that lets those things become active when play touches
them.

## Distillation Method

For each new host or campaign conversion:

1. Identify host entities and persistent state.
2. Identify perception ports and visibility boundaries.
3. Identify resources, costs, and receiving states.
4. Identify jobs, capabilities, relationships, and refusal conditions.
5. Map host endings to canonical T-Stops.
6. Add provenance, witness, and Rest paths.
7. Run a local vertical slice.
8. Record which fields were necessary, redundant, or delightful.
9. Remove host-specific assumptions from the surviving contract.
10. Preserve the smallest physical artifact that still computes the transition.

The reduction is not a rewrite made from guesses:

```text
host encounter
-> Deep Hearth projection
-> witnessed play
-> observed necessity
-> irreducible contract
-> Basin candidate
```

## Current Evidence

The Alpha 4 Responsive Neighborhood demonstrates the first conversion-shaped
crossing:

```text
generic resident
-> baker job
-> first touch
-> knowledge and relationship
-> household and community consequence
-> ecology and terrain response
-> public witness
-> Rest and return
```

The Familiar System demonstrates the same kernel at an interface boundary:

```text
user intent
-> invitation or request
-> familiar interpretation
-> accept, narrow, delay, or refuse
-> bounded operation
-> private or shared result
-> relationship witness
-> repair, Rest, or departure
```

The cards/cardless boundary demonstrates that the physical engine is substrate-
portable:

```text
host material
-> host operation
-> host witness

cardless material
-> Basin operation
-> Basin witness
```

## What Alpha 4 Is Teaching Us

Alpha 4 is not only adding neighborhood content. It is testing whether the
generic kernel can support a world that is:

```text
populated without universal simulation
responsive without arbitrary GM invention
social without a generic relationship score
ecological without population bookkeeping
memorable without carrying the whole world in memory
portable without erasing host law
```

The answer is becoming yes.

## Future Basin Core

The future physical engine should be small enough to fit in a box or folder and
strong enough to host a world:

```text
figures
tokens
dice
cards or slips
cords or threads
ledgers
witness forms
```

Its purpose is not to replace the worlds brought to it. Its purpose is to let
those worlds remain themselves while gaining lawful state, agency, consequence,
memory, and return.

Deep Hearth is where the engine learns what it must be.
